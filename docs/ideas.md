# ainone-ui · 需求池（Idea Backlog）

**用途**：未排期的想法与需求先落在这里。生产者（用户）持续记录原始想法，消费者（实现 Agent）未来按需认领。本文件是「生产端输入」，不约定实现、不承诺期数。

**与计划文档的关系**：

| 文档 | 定位 |
| --- | --- |
| `plan.md` / `plan-v2.md` / `plan-p7-ui.md` | 已批准基线：已排期、含验收标准（AC）、可执行 |
| `docs/ideas.md`（本文件） | 未排期：无验收标准，只记录想法 + 开放问题 |

## 池子约定

### 状态机

一条想法的生命周期：

```text
proposed（已提出，未排期）
  → scheduled（排入某期）→ 迁移到对应 plan 文档，本文件仅留索引
  → dropped（搁置）→ 备注原因，保留不删
```

### 条目模板

| 字段 | 说明 |
| --- | --- |
| 标题 | 一句话点题（含英文名，便于检索） |
| 状态 | proposed / scheduled / dropped |
| 提出日期 | 想法首次记录日期 |
| 优先级 | P1 / P2 / P3（仅参考，非排期承诺） |
| 场景 / 痛点 | 用户在什么情境下遇到什么问题 |
| 需求 | 希望系统「做什么」，不写「怎么做」 |
| 交互方案 | 已定倾向或候选方案对比 |
| 待定项 | 留给实现时澄清的开放问题 |

### 生产 / 消费约定

- 生产者：用户以口语或详述提出，记录时尽量落地为「场景 + 需求 + 方案 + 待定项」四段，不强行补验收标准。
- 消费者：实现 Agent 认领时，**先把它升格为某期的规格书**（指定 F 编号 + AC 条目），再开工——不直接从需求池跳实现。
- 未来若引入生产者-消费者队列编排，本池即队列的输入源。

## 需求列表

### IDEA-001 · 批注式引用提问（Quoted Reply）

| 字段 | 内容 |
| --- | --- |
| 状态 | proposed |
| 提出日期 | 2026-09-02 |

**场景 / 痛点**

1. Agent 回复里某段描述难以理解，用户想针对**这一句**追问，而非重述整个问题。
2. 一次回复中存在多个疑惑点（如开头的观点 A、结尾的观点 C），逐个来回确认需要多次往返对话，低效。
3. 有些疑问很轻（比如某个名词/概念不懂），不值得发起一次「会话级别的对话」去占用宝贵的上下文；希望快速、短上下文地得到解释。

**需求**

以「鼠标选中 Agent 消息中的一段文字」为统一入口，支持三种用法：

- **用法 1（多段批注）**：一次回复内可**框选多处**，各处各自附加疑问；全部批注完成后**一次发送**，作为一条完整请求交给会话内的 Agent（原文片段 + 各条疑问，形成明确引用上下文）。
- **用法 2（单句轻量问答）**：针对**单独一句**选中内容，不占用当前会话上下文，改为调用一个可配置的 endpoint，只把这一句单独交给模型返回一次——上下文极短、响应快。
- **用法 3（悬浮窗即时解释）**：用法 2 的结果以**悬浮窗**形式展示（呼出即问、即看即散），适合即时性问答，不打入消息流、不写日志。

**交互方案**

- **统一入口**：选中文本 → 弹出轻量操作（悬浮工具栏 / 右键菜单），提供「批注」「快速解释」等选项。
- **用法 1（✅ 用户倾向）——批注式**：框选一段文字 → 在该文本旁生成一个批注卡 → 在卡内填入疑问 / 评论 → 继续框选下一处 → 全部完成后统一「发送」一次，把所有批注作为完整请求交给 LLM。
- **用法 1 备选——标记式**：仅高亮标记选中的文本，最后回到原始输入框统一补充描述。用户认为不如批注式直观，暂作备选。
- **用法 2/3**：选中后直接调 endpoint → 结果以**悬浮窗**（浮在选中点附近 / 固定角）呈现，可关闭、可复制；不问入会话。

**待定项（留给实现时澄清，当前不决）**

1. 批注卡的视觉承载形式：跟随文本的悬浮卡 / 独立侧栏列表 / 行内插入？
2. 批注与消息体的联动：消息滚动、thinking 折叠、历史回填后，批注如何保持与原文的挂载关系？
3. 用法 1 发送后引用语的回显方式：气泡内嵌引用块？缩进引用样式？
4. 交互时序：选中即生成批注卡，还是先收集多处统一生成？
5. 与 steering（运行中插话）的关系：批注发送是否同样支持打断当前 turn？
6. 用法 1 的 ACP 协议层传递方式：引用原文拼进 `prompt` 纯文本，还是结构化 content block？
7. 原文定位：选中得到的是 Markdown 渲染后的文本，如何映射回原始消息内容与片段位置？
8. **用法 2/3 的 endpoint**：这个「可配置的 endpoint」是复用当前 harness 的模型接口，还是独立配置一个轻量模型端点？配置字段、鉴权、超时如何定？
9. **用法 2/3 的边界**：快速解释走独立 endpoint 不写消息日志，是否意味着无法追溯？是否需要单独留一个「查询快问」的轻量记录？
10. 三种用法是否共享同一个「选中文本」数据结构，能否合并设计（与 IDEA-003 文件引用一并考虑）？

### IDEA-002 · 右侧元数据侧栏（Session Metadata Panel）

| 字段 | 内容 |
| --- | --- |
| 状态 | proposed |
| 提出日期 | 2026-09-02 |

**场景 / 痛点**

对话过程中用户缺少一个「当前会话是什么状态」的直观视图：不知道当前占用了多少上下文、跑到了哪一步、连的是哪个模型、session 归属哪个工作区，都要靠猜测或翻日志。

**需求**

- 在页面右侧增加一个侧边栏区域，集中展示当前会话的元数据。
- 首份清单（用户已列，可按需扩充）：
  - 进度 / 运行状态（当前 turn 进行到哪一步）
  - **session ID**
  - 当前使用的**模型**
  - （可扩展）harness / adapter、工作区 cwd、消息数、工具调用统计、耗时、token 用量、权限模式等
- **上下文详细面板（重点）**：在元数据中单列一块「上下文」详情，展示当前 session 的上下文占用明细，而非只给一个百分比。参考 DeepChat `contextBudget` 的字段粒度：
  - 可用上下文总量（usable context length）
  - 已用 / 预估输入 token（input tokens，含对话历史、附件、工具 schema 预留、系统提示各自的贡献拆分）
  - 输出余量（剩余可输出 token / effective max output）
  - 各类输入占用明细（未归属输入、工具 schema 预留等各占多少）
  - 越界或缺额时的明确提示（如「上下文不足，建议压缩/缩短输入」）
- 提供「在右侧边栏显示」的开关或可折叠，避免默认占用版面。

**交互方案**

- 右栏作为与左侧（工作区/会话列表）对称的第二侧栏，可独立折叠。
- 元数据展示形态：键值列表 / 分组卡片均可，实现时定。

**待定项（留给实现时澄清）**

1. 数据来源：哪些字段已能从 ACP / harness / 本地日志取到，哪些需新增采集？（如上下文占用、模型名、进度）
2. **上下文明细的可得性**：DeepChat 的 `contextBudget` 分项数据（工具 schema 预留、未归属输入等）是本客户端可自行估算，还是依赖 harness 上报？（AionUi / DeepChat 都各有上下文统计，但口径不同——需确认我们 ACP 侧能拿到什么）
3. 与右侧已有区域（若 P7 后续引入）的关系是否冲突、是否复用同一栏位？
4. 默认展开还是折叠？移动窄窗如何隐藏？
5. 元数据字段的扩展机制：固定清单 vs 插件式注册，避免每次加字段都改一版 UI？

### IDEA-003 · 文件引用（File Attachment / Drag-drop）

| 字段 | 内容 |
| --- | --- |
| 状态 | proposed |
| 提出日期 | 2026-09-02 |

**场景 / 痛点**

用户想让 Agent 围绕某个/某些本地文件工作（作为「引用」上下文），当前只能手敲路径或在 prompt 里描述，不便且易错。

**需求**

- 在消息输入栏上方增加「添加文件」按钮。
- 点击后选择本地文件，作为本次消息的引用附加。
- 同时支持**文件拖拽**：把文件拖到对话框区域直接附上。
- 两种方式（按钮选择 / 拖拽）后续走**同一条路径**：文件被加入「待发送附件」集，随消息一并提交给 Agent。

**交互方案**

- 输入框上方/内部呈现已附加文件的胶囊列表（文件名 + 移除 ×）。
- 拖拽到对话框时高亮反馈（释放即附上）。

**待定项（留给实现时澄清）**

1. 文件如何传给 Agent：仅把路径作为引用传给 harness？还是通过 ACP 提供文件内容/附件能力？
2. 支持范围：文本文件、代码、任意二进制？二进制如何处理（拒绝 / 仅路径 / 转存）？
3. 引用语义：Agent 拿到的是「路径字符串」还是「文件内容注入上下文」？关系到 token 消耗。
4. 拖拽命中区域：输入框本身 / 整个对话框 / 消息区？
5. 附件与 IDEA-001（批注引用）是否共享同一「引用」数据结构，能否合并设计？
6. 多文件顺序、去重、大小上限、超出上下文时的提示。

### IDEA-004 · 会话与 harness 绑定 + 后台并行（Session↔Harness Binding & Background Parallelism）

| 字段 | 内容 |
| --- | --- |
| 状态 | proposed |
| 提出日期 | 2026-09-02 |

**场景 / 痛点**

不同 harness 框架的 session 互不通用——即使是同一个 cwd 工作目录下，OMP 开的会话也不能被 Claude Code 复用。用户需要同时用不同 harness 并行工作，来回切换时各自的状态都要在。

**需求**

- 每个历史 session 绑定**启动它时所用的 harness 框架**。
- 点击某条历史 session 时，自动加载它当时启用的那一个 harness（而非当前选中的 harness）。
- 左侧历史列表里可以**同时存在多个不同 harness 的 session**，可并行工作。
- 切到别的 session 时，未显示的 session **仍在后台工作**，随时可切回，状态不丢。
- 每条 session 在左侧用「它自己的 harness logo」做视觉区分。

**交互方案**

- 会话行左侧显示 harness logo（与 IDEA-003 消息流头像同一来源，供视觉区分）。
- session 的 `adapter_id` 已存在索引中（当前实现已记录），本需求诉求的是**视觉区分 + 后台常驻**的强化。

**进程与资源模型（2026-09-02 已定决策）**

- **采用模型 A：1 个 session = 1 个 harness 子进程**（即现状）。每个会话各自 spawn 进程、各自 `initialize` + `session/new`，靠**进程级隔离**保证「消息互不串扰」（对应 P2 验收 AC-P2-3）。同一条工作目录下可同时跑多个 session = 多个独立进程，互不相干。
- **超时回收**：某 session 持续若干分钟（阈值待定，如 5 分钟）无任何交互（无新 prompt、且无运行中的 turn）→ 回收其子进程；再次点开该 session 时重新 spawn + `session/load` 恢复上下文（配合已实现的消息日志回填，不丢历史）。
- **参考方案 B（进程复用，暂不采用，留作后续升级路径）**：DeepChat 式——按 `agentId::workdir` 复用同一个活着进程，在同一条 ACP 连接上多次 `session/new` 开多个 session。优点：进程数少、内存省、开新会话免 `initialize` 握手。代价：进程级隔离降为 ACP 协议内 sessionId 软隔离，一个进程崩溃连累其上所有 session。留作后续若遇「进程数 / 内存」瓶颈时再评估。

**待定项（留给实现时澄清）**

1. 超时回收的阈值与判定：多少分钟「无交互」算空闲？回收时机上若碰巧有运行中的 turn，是等它完成、强制杀、还是暂缓回收？
2. 状态不丢的保障：切走再切回，是否依赖「消息日志回填」（已实现）+ 子进程常驻？交错多次切换的边界？超时回收后重载的体验（加载耗时可否接受）？
3. 视觉区分的落点：仅 logo 够吗？是否需要 hover/聚焦时显示 harness 名称？
4. 与 P5「工作区」分组的关系：同一工作区下多个 harness 的 session 如何排列、排序规则？
5. 会话与 harness 的绑定是否始终不可改？（区别于历史诉求：某 harness 无法打开的 session 能否换 harness 重开？）

### IDEA-005 · 会话分叉（Conversation Fork）

| 字段 | 内容 |
| --- | --- |
| 状态 | proposed |
| 提出日期 | 2026-09-02 |

**场景 / 痛点**

Agent 在某一轮同时给出多种方案，用户想**分开验证**，之后再回到分叉点重选方向；或对同一句话想跑多个不同方向的探索。当前要么原路重来，要么污染原会话。

**需求**

- 在某一轮对话处**发起分叉（fork）**：以该点之前的历史为基底，新开出一个会话。
- 新会话**接续分叉点继续聊**，往前走自己的方向。
- **不影响原 session**：原会话保持原样，分叉会话独立演化。
- 同一个 session 可 fork 出**多个分叉**，各自探索不同方向，互不影响。

**交互方案**

- 在某条消息上提供「从这里分叉 / Fork」入口（如消息 hover 操作行）。
- 分叉出的会话作为新条目出现在侧栏，视觉上可标注「从 XX 分叉而来」的关联。

**待定项（留给实现时澄清）**

1. 协议可行性：ACP / harness 是否支持「从某历史点复制上下文」的 fork 语义？还是需要客户端在本地重放历史 + 新开 session？——**已探明（2026-09-02）：ACP 后端支持 fork**。DeepChat 走 `forkSession(sessionId, messageId)` 原生能力；AionUi 注释明确「HEAD-fork backends (claude/ACP)」+「fork-anchor 解析（nearest backend_turn_id）」——即 ACP 侧按 `backend_turn_id` 定位分叉锚点，客户端无需本地重放。
2. 分叉后的上下文边界：新会话拿到的历史是「分叉点之前的完整快照」还是「含分叉点这条消息」？
3. 原 session 后续若继续演化，与已分叉出去的分支如何关联展示（树形？平铺 + 标注来源）？
4. 分叉链的元数据：记录父会话、分叉点位置、创建时间，以支持回溯与导航。
5. 与 session/load、消息日志的关系：分叉会话自己的日志如何初始化？

### IDEA-006 · 消息回溯（Rewind / Checkpoint Rollback）

| 字段 | 内容 |
| --- | --- |
| 状态 | proposed |
| 提出日期 | 2026-09-02 |

**场景 / 痛点**

Agent 走到某个阶段后，用户发现方向不对或文件被改坏，想回到自己**某一条消息**所处的那一刻，从那里重新开始——而不是重新开会话从零再来，也不是污染当前会话往回硬滚。

**需求**

- 针对**用户自己的某一条消息**发起「回溯」，恢复到那条消息发出时的状态。
- **分两种情况**：
  1. **只回溯上下文**——对话上下文回到那条消息之前，工作目录里已经产生的文件修改**保留不动**；
  2. **回溯上下文 + 文件修改**——对话上下文和文件改动**一起**回滚到那一刻。
- 回溯后以该点为基底继续对话（与 IDEA-005 分叉不同：分叉是「另开新枝」，回溯是「回到主干这个点重走」——二者关系待定项澄清）。

**交互方案**

- 用户消息 hover 操作行提供「回溯到这里」入口。
- 回溯前给明确确认，尤其情况二是破坏性操作（会动文件），须显著提示与二次确认。

**待定项（留给实现时澄清）**

1. 文件回滚的可行性：harness 是否有改动历史 / 快照？否则客户端需自己为每次文件修改维护快照（成本高），或依赖外部 `git` / 文件系统快照。
2. 回溯与「本地消息日志」的关系：日志是按序追加的，回溯是否截断日志？还是日志保留全集、另记回溯点？
3. 情况一（只回上下文）与情况二（回上下文+文件）的 UI 如何区分、如何在同一入口下二选一。
4. 与 IDEA-005 分叉的边界：回溯破坏原会话吗？分叉是否其实是「回溯 + 新开」的等价物？两者是否应合并为一个会话树的两种操作？
5. 可回溯的范围：能否回到任意深度？有没有「最近 N 条」或「仅本会话」的约束？
6. harness 协议层是否支持「截断上下文」或「回滚」？还是客户端重放历史到某点 + 丢弃之后的消息？
7. 文件回滚的可逆性：回滚本身是否可撤销（回滚前自动备份）？

### IDEA-007 · 命令队列（Command Queue）

| 字段 | 内容 |
| --- | --- |
| 状态 | proposed |
| 提出日期 | 2026-09-02 |
| 优先级 | P1 |
| 来源 | AionUi `CommandQueuePanel` / `useConversationCommandQueue` |

**场景 / 痛点**

用户一次想交代多件事，但当前只有「打断即发」的单条 steering：要么等 agent 忙完一条一条手动发，要么打断丢掉当前进度。缺少「先排好队、agent 空闲逐条消费」的能力。

**需求**

- 在运行中/空闲时都可把新的指令**追加进一个待执行队列**，而不是立刻打断。
- 队列内的条目可**编辑、删除、拖拽排序**。
- agent 当前 turn 结束后自动**按序消费**下一条。
- 队列有容量上限，超出给明确反馈（不静默丢弃）。
- 队列状态持久化（跨重启不丢）。

**交互方案**

- 发送框上方/旁提供「命令队列」面板入口，展示已排队条目。
- 每条 = 指令预览（单行省略）+ 编辑/删除/拖拽手柄 + 状态（等待中/执行中）。
- 与现有 steering「打断即发」（IDEA-006 之外的行为）并存：用户可选「立即打断发」或「排队」。

**待定项（留给实现时澄清）**

1. 队列消费与 steering 的语义边界：排队的指令何时真正送达（turn 自然结束？还是当前工具执行完毕？复用 F-3-4 的 follow_up 语义？）
2. 队列容量与「queueFull / queueTooLarge」的阈值。
3. 执行中的条目失焦/切走后如何展示进度。
4. 队列入口与主输入框的 UI 层级关系（面板 vs 内联展开）。
5. 指令参数（如文件引用、@会话）进入队列后如何保持完整（AionUi 注释强调「消息经过队列丢失引用是静默失败」）。

### IDEA-008 · 会话内搜索与跳转（In-session Search & Anchor Rail）

| 字段 | 内容 |
| --- | --- |
| 状态 | proposed |
| 提出日期 | 2026-09-02 |
| 优先级 | P1 |
| 来源 | DeepChat `useChatSearch` + AionUi `MessageAnchorRail` |

**场景 / 痛点**

长会话（5000 条级别）里想找回早先的某句话/某个结论，只能手动狂翻。需要全文搜索 + 快速跳转。

**需求**

- 会话内**全文搜索**（消息正文、thinking、工具标题）。
- 命中高亮 + 命中计数 + 「上一条/下一条」键盘导航。
- 结果快速跳转到对应消息位置。
- （可选）右侧**锚点光带**（anchor rail）：把消息锚点（用户消息/工具组/分叉点）标成侧边小点，鼠标悬停显示摘要、点击跳转。

**交互方案**

- 顶部或侧栏提供搜索框（复用全局搜索按钮或快捷键唤起，如 Cmd/Ctrl+F）。
- 命中项列表展示命中片段 + 所属消息摘要；回车跳转。
- anchor rail 为右侧窄条，仅在长会话时显示。

**待定项（留给实现时澄清）**

1. 搜索范围与索引：本地消息日志（已实现）全文扫，还是需要额外倒排索引？5000 条规模下性能？
2. 与「消息虚拟列表」的配合：跳转到未渲染的消息如何滚动定位（复用锚点 id 机制）。
3. 搜索高亮的生命周期：新消息流式到达时如何避免高亮串位。
4. anchor rail 与 IDEA-005 分叉点、IDEA-006 回溯点的锚点体系是否统一。
5. 快捷键冲突（与 slash 补全、全局搜索、Ink 输入等）。

| --- | --- |
| 状态 | proposed |
| 提出日期 | 2026-09-02 |
| 优先级 | P1 |
| 来源 | AionUi `ConversationPlanBar` |

**场景 / 痛点**

agent 拟定 plan / 待办 后开始执行，用户看不到「现在进行到哪一步、还剩几项」。plan 若作为消息流进对话，会随后续消息被冲走；若闷进 thinking 折叠又不够直观。
