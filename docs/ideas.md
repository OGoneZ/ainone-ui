# ainone-ui · 需求池（Idea Backlog）

**用途**：未排期的想法与需求先落在这里。生产者（用户）持续记录原始想法，消费者（实现 Agent）未来按需认领。本文件是「生产端输入」，不约定实现、不承诺期数。

**与计划文档的关系**：

| 文档 | 定位 |
| --- | --- |
| `plan.md` / `plan-v2.md` / `plan-p7-ui.md` | 已批准基线：已排期、含验收标准（AC）、可执行 |
| `docs/ideas.md`（本文件） | 未排期：无验收标准，只记录想法 + 开放问题 |

## 池子约定

### 状态机

一条想法的生命周期：

```text
proposed（已提出，未排期）
  → scheduled（排入某期）→ 迁移到对应 plan 文档，本文件仅留索引
  → dropped（搁置）→ 备注原因，保留不删
```

### 条目模板

| 字段 | 说明 |
| --- | --- |
| 标题 | 一句话点题（含英文名，便于检索） |
| 状态 | proposed / scheduled / dropped |
| 提出日期 | 想法首次记录日期 |
| 场景 / 痛点 | 用户在什么情境下遇到什么问题 |
| 需求 | 希望系统「做什么」，不写「怎么做」 |
| 交互方案 | 已定倾向或候选方案对比 |
| 待定项 | 留给实现时澄清的开放问题 |

### 生产 / 消费约定

- 生产者：用户以口语或详述提出，记录时尽量落地为「场景 + 需求 + 方案 + 待定项」四段，不强行补验收标准。
- 消费者：实现 Agent 认领时，**先把它升格为某期的规格书**（指定 F 编号 + AC 条目），再开工——不直接从需求池跳实现。
- 未来若引入生产者-消费者队列编排，本池即队列的输入源。

## 需求列表

### IDEA-001 · 批注式引用提问（Quoted Reply）

| 字段 | 内容 |
| --- | --- |
| 状态 | proposed |
| 提出日期 | 2026-09-02 |

**场景 / 痛点**

1. Agent 回复里某段描述难以理解，用户想针对**这一句**追问，而非重述整个问题。
2. 一次回复中存在多个疑惑点（如开头的观点 A、结尾的观点 C），逐个来回确认需要多次往返对话，低效。

**需求**

- 用鼠标选中 assistant 消息（Agent 回复）中的一段文字。
- 对该段文字附加疑问 / 评论（即「批注」）。
- 一次回复内可**框选多处**，各处各自附加疑问。
- 全部批注完成后，**一次发送**，作为一条完整请求提交给 Agent。
- Agent 收到的请求须包含：被引用的原文片段 + 各条疑问，形成明确的引用上下文，使其针对对应描述作答。

**交互方案**

- **方案一（✅ 用户倾向）——批注式**：框选一段文字 → 在该文本旁生成一个批注卡 → 在卡内填入疑问 / 评论 → 继续框选下一处 → 全部完成后统一「发送」一次，把所有批注作为完整请求交给 LLM。
- **方案二（备选）——标记式**：仅高亮标记选中的文本，最后回到原始输入框统一补充描述。用户认为不如方案一直观，暂作备选。

**待定项（留给实现时澄清，当前不决）**

1. 批注卡的视觉承载形式：跟随文本的悬浮卡 / 独立侧栏列表 / 行内插入？
2. 批注与消息体的联动：消息滚动、thinking 折叠、历史回填后，批注如何保持与原文的挂载关系？
3. 发送后引用语的回显方式：气泡内嵌引用块？缩进引用样式？
4. 交互时序：选中即生成批注卡，还是先收集多处统一生成？
5. 与 steering（运行中插话）的关系：批注发送是否同样支持打断当前 turn？
6. ACP 协议层传递方式：引用原文拼进 `prompt` 纯文本，还是结构化 content block？
7. 原文定位：选中得到的是 Markdown 渲染后的文本，如何映射回原始消息内容与片段位置？

### IDEA-002 · 右侧元数据侧栏（Session Metadata Panel）

| 字段 | 内容 |
| --- | --- |
| 状态 | proposed |
| 提出日期 | 2026-09-02 |

**场景 / 痛点**

对话过程中用户缺少一个「当前会话是什么状态」的直观视图：不知道当前占用了多少上下文、跑到了哪一步、连的是哪个模型、session 归属哪个工作区，都要靠猜测或翻日志。

**需求**

- 在页面右侧增加一个侧边栏区域，集中展示当前会话的元数据。
- 首份清单（用户已列，可按需扩充）：
  - 上下文占用（当前位置 / 总量，例如 token 或百分比进度条）
  - 进度 / 运行状态（当前 turn 进行到哪一步）
  - **session ID**
  - 当前使用的**模型**
  - （可扩展）harness / adapter、工作区 cwd、消息数、工具调用统计、耗时、token 用量、权限模式等
- 提供「在右侧边栏显示」的开关或可折叠，避免默认占用版面。

**交互方案**

- 右栏作为与左侧（工作区/会话列表）对称的第二侧栏，可独立折叠。
- 元数据展示形态：键值列表 / 分组卡片均可，实现时定。

**待定项（留给实现时澄清）**

1. 数据来源：哪些字段已能从 ACP / harness / 本地日志取到，哪些需新增采集？（如上下文占用、模型名、进度）
2. 与右侧已有区域（若 P7 后续引入）的关系是否冲突、是否复用同一栏位？
3. 默认展开还是折叠？移动窄窗如何隐藏？
4. 元数据字段的扩展机制：固定清单 vs 插件式注册，避免每次加字段都改一版 UI？

### IDEA-003 · 文件引用（File Attachment / Drag-drop）

| 字段 | 内容 |
| --- | --- |
| 状态 | proposed |
| 提出日期 | 2026-09-02 |

**场景 / 痛点**

用户想让 Agent 围绕某个/某些本地文件工作（作为「引用」上下文），当前只能手敲路径或在 prompt 里描述，不便且易错。

**需求**

- 在消息输入栏上方增加「添加文件」按钮。
- 点击后选择本地文件，作为本次消息的引用附加。
- 同时支持**文件拖拽**：把文件拖到对话框区域直接附上。
- 两种方式（按钮选择 / 拖拽）后续走**同一条路径**：文件被加入「待发送附件」集，随消息一并提交给 Agent。

**交互方案**

- 输入框上方/内部呈现已附加文件的胶囊列表（文件名 + 移除 ×）。
- 拖拽到对话框时高亮反馈（释放即附上）。

**待定项（留给实现时澄清）**

1. 文件如何传给 Agent：仅把路径作为引用传给 harness？还是通过 ACP 提供文件内容/附件能力？
2. 支持范围：文本文件、代码、任意二进制？二进制如何处理（拒绝 / 仅路径 / 转存）？
3. 引用语义：Agent 拿到的是「路径字符串」还是「文件内容注入上下文」？关系到 token 消耗。
4. 拖拽命中区域：输入框本身 / 整个对话框 / 消息区？
5. 附件与 IDEA-001（批注引用）是否共享同一「引用」数据结构，能否合并设计？
6. 多文件顺序、去重、大小上限、超出上下文时的提示。

### IDEA-004 · 会话与 harness 绑定 + 后台并行（Session↔Harness Binding & Background Parallelism）

| 字段 | 内容 |
| --- | --- |
| 状态 | proposed |
| 提出日期 | 2026-09-02 |

**场景 / 痛点**

不同 harness 框架的 session 互不通用——即使是同一个 cwd 工作目录下，OMP 开的会话也不能被 Claude Code 复用。用户需要同时用不同 harness 并行工作，来回切换时各自的状态都要在。

**需求**

- 每个历史 session 绑定**启动它时所用的 harness 框架**。
- 点击某条历史 session 时，自动加载它当时启用的那一个 harness（而非当前选中的 harness）。
- 左侧历史列表里可以**同时存在多个不同 harness 的 session**，可并行工作。
- 切到别的 session 时，未显示的 session **仍在后台工作**，随时可切回，状态不丢。
- 每条 session 在左侧用「它自己的 harness logo」做视觉区分。

**交互方案**

- 会话行左侧显示 harness logo（与 IDEA-003 消息流头像同一来源，供视觉区分）。
- session 的 `adapter_id` 已存在索引中（当前实现已记录），本需求诉求的是**视觉区分 + 后台常驻**的强化。

**待定项（留给实现时澄清）**

1. 后台常驻的资源开销：N 个 session 同时跑 = N 个子进程，是否需要「空闲挂起 / 超时回收」策略？
2. 状态不丢的保障：切走再切回，是否依赖「消息日志回填」（已实现）+ 子进程常驻？交错多次切换的边界？
3. 视觉区分的落点：仅 logo 够吗？是否需要 hover/聚焦时显示 harness 名称？
4. 与 P5「工作区」分组的关系：同一工作区下多个 harness 的 session 如何排列、排序规则？
5. 会话与 harness 的绑定是否始终不可改？（区别于历史诉求：某 harness 无法打开的 session 能否换 harness 重开？）

### IDEA-005 · 会话分叉（Conversation Fork）

| 字段 | 内容 |
| --- | --- |
| 状态 | proposed |
| 提出日期 | 2026-09-02 |

**场景 / 痛点**

Agent 在某一轮同时给出多种方案，用户想**分开验证**，之后再回到分叉点重选方向；或对同一句话想跑多个不同方向的探索。当前要么原路重来，要么污染原会话。

**需求**

- 在某一轮对话处**发起分叉（fork）**：以该点之前的历史为基底，新开出一个会话。
- 新会话**接续分叉点继续聊**，往前走自己的方向。
- **不影响原 session**：原会话保持原样，分叉会话独立演化。
- 同一个 session 可 fork 出**多个分叉**，各自探索不同方向，互不影响。

**交互方案**

- 在某条消息上提供「从这里分叉 / Fork」入口（如消息 hover 操作行）。
- 分叉出的会话作为新条目出现在侧栏，视觉上可标注「从 XX 分叉而来」的关联。

**待定项（留给实现时澄清）**

1. 协议可行性：ACP / harness 是否支持「从某历史点复制上下文」的 fork 语义？还是需要客户端在本地重放历史 + 新开 session？
2. 分叉后的上下文边界：新会话拿到的历史是「分叉点之前的完整快照」还是「含分叉点这条消息」？
3. 原 session 后续若继续演化，与已分叉出去的分支如何关联展示（树形？平铺 + 标注来源）？
4. 分叉链的元数据：记录父会话、分叉点位置、创建时间，以支持回溯与导航。
5. 与 session/load、消息日志的关系：分叉会话自己的日志如何初始化？

### IDEA-006 · 消息回溯（Rewind / Checkpoint Rollback）

| 字段 | 内容 |
| --- | --- |
| 状态 | proposed |
| 提出日期 | 2026-09-02 |

**场景 / 痛点**

Agent 走到某个阶段后，用户发现方向不对或文件被改坏，想回到自己**某一条消息**所处的那一刻，从那里重新开始——而不是重新开会话从零再来，也不是污染当前会话往回硬滚。

**需求**

- 针对**用户自己的某一条消息**发起「回溯」，恢复到那条消息发出时的状态。
- **分两种情况**：
  1. **只回溯上下文**——对话上下文回到那条消息之前，工作目录里已经产生的文件修改**保留不动**；
  2. **回溯上下文 + 文件修改**——对话上下文和文件改动**一起**回滚到那一刻。
- 回溯后以该点为基底继续对话（与 IDEA-005 分叉不同：分叉是「另开新枝」，回溯是「回到主干这个点重走」——二者关系待定项澄清）。

**交互方案**

- 用户消息 hover 操作行提供「回溯到这里」入口。
- 回溯前给明确确认，尤其情况二是破坏性操作（会动文件），须显著提示与二次确认。

**待定项（留给实现时澄清）**

1. 文件回滚的可行性：harness 是否有改动历史 / 快照？否则客户端需自己为每次文件修改维护快照（成本高），或依赖外部 `git` / 文件系统快照。
2. 回溯与「本地消息日志」的关系：日志是按序追加的，回溯是否截断日志？还是日志保留全集、另记回溯点？
3. 情况一（只回上下文）与情况二（回上下文+文件）的 UI 如何区分、如何在同一入口下二选一。
4. 与 IDEA-005 分叉的边界：回溯破坏原会话吗？分叉是否其实是「回溯 + 新开」的等价物？两者是否应合并为一个会话树的两种操作？
5. 可回溯的范围：能否回到任意深度？有没有「最近 N 条」或「仅本会话」的约束？
6. harness 协议层是否支持「截断上下文」或「回滚」？还是客户端重放历史到某点 + 丢弃之后的消息？
7. 文件回滚的可逆性：回滚本身是否可撤销（回滚前自动备份）？
