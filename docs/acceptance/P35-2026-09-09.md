# P35 验收纪要：流式输出平滑揭示（2026-09-09）

> 分支：`zhubaoduo/perf/p35_stream_pacing`（已 merge 到 main @ 6441c29）
> 规格：`docs/plan-p35-stream-pacing.md`

## 1. 问题与根因

用户反馈：流式输出「隔一会儿突然蹦出来几个字」。量化根因：harness SSE chunk 平均 ~121ms/条（P31 实测 396 条/48s）且突发不均；P31 的 rAF 节流只合并**同一帧内**的多条事件，到达节奏被原样透传——100-200ms 间隔下几十字/次的跳变被人眼感知为卡顿。这是 **pacing 缺失**，不是渲染性能问题。

## 2. 社区调研结论（详见规格书 §1）

- **Vercel AI SDK smoothStream**：服务端重切片、固定 delay、无 catch-up——不适用客户端 ACP 场景。
- **Convex useSmoothText**：时间基 catch-up + EMA 平滑，最简可移植。
- **markstream-core**（DeepChat 在用）：比例控制器 `targetCps = clamp(pending/目标延迟, min, max)` + 积压阈值切短延迟 + EMA + grapheme 切分 + 未闭合 fence 阻塞——**最完整开源实现，采纳其形状**。
- **性能预算共识**：提交帧率 20-30fps（逐字符 60fps 是浪费）；真正瓶颈在 markdown 重解析；揭示粒度按 `cps×dt` + 单帧上限。

## 3. 实现

| 组件 | 职责 |
|---|---|
| `streamPacer.ts` | 比例控制器：`targetCps = clamp(pending/latency, 40, 2000)`；pending>600 切 350ms catch-up；EMA 0.2 平滑；`charBudget += cps×dt`；每帧揭示 min(budget, 120) 字素；commitFps 30 跳帧；fence 门（闭合事件携带阻塞区整体回吐保时序）；reduced-motion 直通 |
| `revealScheduler.ts` | pacer 的**自持帧时钟**——P31 throttle 只在事件到达时排帧，SSE 空窗期揭示会停滞（「隔一会蹦字」的另一半根因）；积压未清时自持 rAF 排帧 |
| `overlayRevealed.ts` | 揭示前缀按块边界映射回 blocks：完整揭示块引用不变（Streamdown memo 命中），尾块取剩余，未揭示置空；tool/thought 块直通（状态即时性优先） |
| ChatPanel 接线 | agent_text 喂 pacer；turn 收口 finally `scheduler.dispose()`（自持帧跨 turn 存活会污染后续 runtime——测试实证）；零事件 turn commit 守卫不新起空气泡 |

## 4. 测试证据

- streamPacer 10 例：匀速分帧、终态完整、catch-up 升档、grapheme 不切半、fence 阻塞/闭合/flush、跳帧、396 条回放（提交 ≤ 30fps×时长）、reduced-motion、突发不倾泻。
- overlay 5 例 + scheduler 4 例（自持循环、空窗不停滞、flush 收口、dispose）。
- 全仓 `pnpm test` **695 用例全绿**（含 P31 节流、P32 性能系列、P34 可见性全部既有防回归）；`tsc` 零错误；`pnpm build` 通过。

## 5. 实机冒烟（webdriver 4445，生产窗口）

- 建会话 → 发消息（气泡上屏）→ 分屏 → 焦点切换 → 失焦窗格消息完整、无白屏：**PASS**（P34 语义无回归）。
- 流式平滑度为体感项，需真实 harness 流式会话肉眼验收（本机 adapter 未配置真实流式）——算法节奏已由 396 条回放测试锁定（30fps 匀速、终态完整）。

## 6. 参数速查（后续调优入口）

`streamPacer.ts DEFAULTS`：minCps 40 / maxCps 2000 / targetLatencyMs 900 / catchUpLatencyMs 350 / catchUpThreshold 600 / commitFps 30 / maxCharsPerCommit 120。嫌慢调低 targetLatencyMs；嫌跳调低 maxCharsPerCommit。
